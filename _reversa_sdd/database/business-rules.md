# Database Business Rules — GER

> Generated by Reversa (Data Master) on 2026-04-28
> Phase: Revisão (Agente Independente)

Como o sistema utiliza mecanismos leves de persistência (DuckDB em memória e arquivos SQLite locais), a maioria das regras de negócio é mantida nas camadas de **Domínio** e **Aplicação**, evitando lógica embarcada em procedures ou triggers.

## 1. Integridade e Constraints de Aplicação

### Data Contract Healthcheck (Shift-Right)
- **Onde**: `DuckDBAnalyticsRepository`
- **Regra**: Toda inicialização do repositório valida o schema contra colunas clínicas críticas (`numeroCMCE`, `entidade_classificacaoRisco_cor`, `entidade_especialidade_descricao`, etc.). Se violado, lança um erro imediatamente (`DataNotReadyError`), impedindo consultas inconsistentes.

### Watermarking (Controle de Duplicidade)
- **Onde**: `SQLiteRawRepository.get_watermark`
- **Regra**: Garante idempotência capturando o maior `data_alteracao` processado para cada fila do Gercon, evitando loops redundantes.

## 2. Segurança e RLS (Row-Level Security)

- **Onde**: `_get_rls_cte` na query DuckDB.
- **Lógica**: Implementado via CTE dinâmico (`WITH BaseRLS AS (...)`). Filtra os dados clínicos com base no escopo de autenticação provido pelo token IAP do usuário médico antes de expor as linhas para agregação analítica.
