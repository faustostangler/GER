# Architecture Overview — GER

> Generated by Reversa (Architect) on 2026-04-28
> Level: Detailed

## 1. Architectural Style
O GER é projetado como um **Modular Monolith** seguindo os princípios de **Hexagonal Architecture** (Clean Architecture) e **Domain-Driven Design (DDD)**.

### Core Separation
- **Domain**: Entidades puras (`DoctorProfile`, `IngestionLogEntry`), Value Objects (`ClinicaPolicy`, `MedicalCouncilRegistration`) e Especificações (`FiltroAvancadoSpec`). Totalmente independente de frameworks.
- **Application**: Casos de uso (`AnalyticsUseCase`, `ScraperUseCase`) orchestrando regras de negócio e interagindo via Ports (Interfaces).
- **Infrastructure**: Adapters concretos para persistência (DuckDB, SQLite), filas (DLQ), scraping (Playwright) e telemetria (Prometheus, Sentry).

## 2. Technology Stack
- **Frontend/BFF**: Streamlit & FastAPI.
- **Data Layer**: DuckDB (OLAP queries) e PyArrow IPC (Redis Feather Cache).
- **Identity**: Keycloak (OIDC) + OAuth2-Proxy.
- **Messaging**: Redpanda (Kafka API) para validações assíncronas.

## 3. Technical Debt & Observations
- **Module Identity Mismatch**: Risco conhecido no Python `match/case` ao misturar caminhos absolutos e relativos (`src.domain` vs `domain`).
- **Redis Graceful Degradation**: O sistema deve continuar operando via Parquet direto se o cache Redis falhar.
